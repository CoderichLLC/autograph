GQL:Request -> Business Logic -> GQL:Response -> SideEffects

* context.autograph.resolver is used in GQL custom resolver methods.
  therefore it should share the absolute root Resolver that was generated upon GQL:Request (ie. never overridden)
  because it is actually an integral "part" of the incoming request

* postQuery/Mutation hooks are used to generate potential side-effects **that are part of the request**
  because of the nature of GQL selecting any subdocument(s) you may need external data set as part of the request
  you use a post* hook because you want to wait/ensure the root operation actually happened (eg. postMutation on User)
  it's a philisophical question if it should be part of the root session or not.
    My hunch says yes. If you want isolation you can use .transaction() or you can use "postResponse"

* Right now pre/post Response are incorrect conceptually.
  The event should fire right before and after GQL:Response (eg. the server responding to the request)
  This allows the API to return data quickly and SideEffects to happen truely out of band

* postResponse should absolutely be in it's own transaction - it feels absolutely unrelated/detached from the initial request
